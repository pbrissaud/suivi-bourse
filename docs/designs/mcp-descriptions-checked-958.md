## Problem Statement

The six MCP tool descriptions in `src/application/mcp_server.py` are the only
thing an agent reads to know what a payload carries, and nothing checks that
they are true. #955 corrected eight false claims in three review cycles, seven
of them found by driving the tools, none by reading. `tests/test_mcp_server.py`
asserts that sentences *are present*; it cannot say whether they are *true*.

Two facts found during this session change the shape of the answer:

- **The server already publishes an `outputSchema`, and it is empty.** Every
  tool is annotated `-> Dict[str, Any]`, so `tools/list` advertises
  `{"result": {"type": "object", "additionalProperties": true}}`. The ticket's
  "an MCP agent gets no schema" is true only because of that annotation — the
  protocol carries one.
- **`unit_cost`, `market_value` and `plus_value_latente` do exist** — on the
  *shares* payload (`portfolio_view.py:39-43`), not on `list_positions`. That
  is very probably where #955's wrong wording came from. Any check must be
  **per tool**, never against the process's whole key vocabulary.

## Premises (agreed)

1. **The acceptance criterion is 2 of 4, not 4 of 4** (agreed at 3, revised
   by the spec review). `unit_cost` / `market_value` are named keys the row
   does not carry: caught by the forward check. The currency of `price` /
   `fundamentals.market_cap` is caught by the reverse direction, because
   `price.currency` and `fundamentals.currency` must be cited. **Not caught:**
   the gain terms — the pre-#955 prose said "four terms" and named no member,
   so no key check can see it — and the TWR anchor claim (#887), a relation
   between values. The ticket must say both rather than claim them.
2. **The check is only as good as its fixture.** `twr_since`, `taxation_kind`,
   the `projected_*` members, `closed_at`, `ytd` and `market_cap` are absent by
   design until data produces them. A rich fixture must make every optional
   member appear at least once, and the test must assert that it does.
3. **Both directions.** A member cited must be served, and a member served
   must be cited — the second catches a member added to a builder while the
   description stays behind.
4. **The behavioural half (model + judge) is dropped**, not deferred to a twin
   ticket. The repo has deliberately no eval lane.

## Approaches Considered

- **A — backticks checked against the observed payload only.** Ruled out in
  favour of C: exact, but leaves the agent with the empty schema it has today.
- **B — regex over the unchanged prose.** Ruled out: members of one word
  (`quantity`, `realised`, `xirr`, `ytd`, `months`) cannot be told from
  English, so `price` or `day` pass "cited" by accident and an invented
  one-word member is never caught.
- **C — typed returns, so a real `outputSchema`; citations in backticks.**
  Chosen.

## Recommended Approach — C

### 1. Each payload is a `TypedDict`, and each tool returns one

Declare every payload shape in `mcp_server.py`, the one module that reads them
(eng review S1): position row, price, converted, fundamentals, totals, ytd,
account row, rhythm, month, history point, event row, and the envelope of each
of the six tools. `portfolio_view`, `account_facts` and `rhythm` do not change:
`/api` does not read these types, and a builder drifting from its declaration
fails the transit and schema ⊆ observed tests. Annotate each tool
`-> <Envelope>` instead of `-> Dict[str, Any]`.

The absence rule becomes a schema fact rather than a sentence:

| Payload behaviour | Declared as |
|---|---|
| member always present, may be null | `Optional[T]` (in `required`) |
| member absent rather than null | `NotRequired[T]` |

Per payload: on the **account row**, `taxation_model`, `opened_on`,
`first_payment`, `twr_since`, `taxation_kind` and the `projected_*` members are
`NotRequired` (`declared_only` drops them when None). On **totals**,
`twr_since` is always present and `Optional`. The implementer reads each
builder and records any other omit-when-None member the same way.

**Types are as wide as the builder, and no wider in kind.** Probed on mcp
2.1.1: the SDK validates `structured_content` through pydantic — `"3"` became
`3.0`. A value that fails validation turns a read into an error, so every
member that can be missing is `Optional`. But the kind is kept: `int` stays
`Optional[int]` (`months_covered`, `months_observed`, `total`, `returned`),
`bool` stays `bool` (`terminal`, `declared`), and `float` is used only for real
floats — `Optional[float]` on an int would serve `6.0` for `6`, which changes
what the tool returns.

The history envelope has a `from` key, a Python keyword: declare it with the
functional form `TypedDict('HistoryEnvelope', {'from': str, 'to': str, ...})`
(probed: works).

`/api` is unaffected: a `TypedDict` is an annotation, and
`account_facts.accounts_payload`, shared with `/api/accounts`, builds the same
dict at runtime. What the tools return does not change (ticket: out of scope).

### 2. The guard the SDK makes necessary: nothing dropped in transit

Probed on mcp 2.1.1: **a key the `TypedDict` does not declare is silently
removed from `structured_content`**, while the text block sent beside it still
carries it. The two channels diverge, and nothing raises.

So the first test, per tool on the rich fixture: `json.loads(text) ==
structured_content`, with Python equality, so `5 == 5.0` passes, and a dropped
key, a changed value or a string coerced to a number fails (eng review R4). The
text block itself does not change a byte: it is the raw return, serialised
before the SDK's validation.
A member added in `portfolio_view._build_position` without a declaration fails
here, which is the ticket's "a member renamed or removed fails a test" in its
sharpest form.

Also: the envelope loses its `result` wrapper (a `TypedDict` schema is inlined
at the root). `payload()` in `tests/test_mcp_server.py` reads
`structured_content['result']` and changes once, in that one place.

### 3. Citations are in backticks, and each resolves

**A backtick means "served", and nothing else.** Every member a description
cites as present is written in backticks: `` `quantity` ``,
`` `price.currency` ``, `` `ytd.twr` ``. A negation is written **without**
backticks ("THERE IS NO market_value MEMBER"), so "the row carries
`` `unit_cost` ``" — #955's lie in the new convention — fails. This covers the
six descriptions, the shared `_CURRENCY` / `_ABSENCE` paragraphs, and the
server instructions; the latter belong to no tool, so their tokens must use
the `tool.path` form. `` `projected_*` `` becomes the explicit list of the
members it stands for.

The test extracts **every** backtick span, from the description **as listed
by the client** (the existing `listed()` helper). A span that does not match
`[a-z_][a-z0-9_]*(\.[a-z_][a-z0-9_]*)*` fails the test rather than being
skipped. Each token must resolve to **at least one** of, checked in order
(`` `symbol` `` on `list_events` is both an argument and `events[].symbol`):

1. a tool name (`tools/list`);
2. a property of that tool's `input_schema` (`from_day`, `to_day`, `symbol`,
   `limit`) — served by the protocol, so checked, not exempted;
3. a path in that tool's `output_schema`, walked through `$defs`, `anyOf` and
   array `items`, and matched by the §4 resolver: the full spelling, or a
   partial suffix naming **exactly one** path (`price.currency` names
   `positions[].price.currency`; a bare `currency` names three and fails —
   eng review R2);
4. `<tool>.<path>` — a member of **another** tool, resolved in that tool's
   schema. Needed where a description sends the reader elsewhere
   ("`list_positions.realised` per holding").

There is no hand-kept list. What keeps a negation honest is the converse
rule: **a `snake_case` or dotted token outside backticks that the same
resolver maps to a path of the tool's schema — or, for a `tool.path` token, of
the named tool's schema — fails the test.** If `market_value` is one day served,
"THERE IS NO market_value MEMBER" breaks the suite instead of lying. (One-word
members cannot be told from English outside backticks and are not checked
there.)

### 4. The reverse direction: every served member is cited

Every property path of each tool's `output_schema` must appear in backticks in
that tool's description. **One resolver serves every rule in this doc:** a
token counts for a path when it equals that path's full spelling with `[]`
removed (`` `monthly_amount` `` is the rhythm's root member,
`` `accounts.monthly_amount` `` the per-account one), or when it is a partial
suffix matching **exactly one** path of that schema. A bare `` `currency` ``
matches `price.currency`, `converted.currency` and `fundamentals.currency`, so
it counts for none of them. This grows the
prose where it is silent today — `fundamentals.sector`, `price.at`,
`converted.rate_at`, the event row's members, `months[].month` — and that is
accepted: it is also what the agent needs.

This is also what catches the currency defect mechanically: `price.currency`
and `fundamentals.currency` must be cited, and reverting #955 removes them.

### 5. One rich fixture, and a test that it stays rich

A fixture in `tests/test_mcp_server.py`, built with the helpers the file
already has (`build_runtime`, `quotes.record_quote`, the perf pass used by the
`twr_since` tests) and the tax fixtures of `tests/test_taxation_projection.py`:
a USD instrument on an EUR base, a sold position (`closed_at`), fundamentals
with `market_cap`, a declared account with an opening day, a payment and a
valid projecting taxation model whose rate change is still ahead
(`projected_rate_changes_on`), a series that crosses a year end (`ytd`), and
twelve months of buys. **Every fixture date is relative to `date.today()`**:
`rhythm`'s window and `ytd` both end today, and fixed dates would rot.

The test asserts **schema ⊆ observed**: every path of every `output_schema` is
seen at least once across the six calls on that fixture. A `TypedDict` member
that no builder ever emits fails, and so does a fixture that rots.

## Two traps the typed return brings, probed on mcp 2.1.1

- **A refused value reaches the agent as a bare failure.** A builder that emits
  `None` where the `TypedDict` says `float` yields `is_error: true` and the text
  `"Error executing tool bad"` — no reason. The validation runs *after* the
  tool body returns, so `reading()` cannot catch it. That breaks the repo's
  rule that every fault arrives in words
  (`test_a_storage_fault_arrives_in_words_and_not_as_a_bare_failure`).
  **Consequence: every number and every string that can be missing is declared
  `Optional`**, and nothing stricter is declared than what the builder is
  proven to emit. The rich-fixture tests exercise every path, so a mismatch
  fails in the suite, not in front of the owner.
  **And what the fixture did not foresee still arrives in words** (eng review
  R3). Each tool's envelope has a module-level `TypeAdapter`, and
  `reading(work, envelope)` validates the body's return before the SDK does. A
  `pydantic.ValidationError` is caught in its own branch, **before** the
  `ValueError` one, because it subclasses `ValueError` and would otherwise read
  "the store could not answer". It raises a `ToolError` that says the answer
  did not match its schema and carries pydantic's reason. All six bodies go
  through `reading()`, `list_events` and `get_investment_rhythm` included.
  Test: a value of the wrong kind, injected into a builder's output, gives
  `is_error` with those words.
- **A NaN in a non-optional `float` breaks the client.** Pydantic dumps NaN as
  `null` in JSON mode, and the *client* then refuses the structured content
  (`RuntimeError: None is not of type 'number'`) — the call raises instead of
  answering. Under `Optional[float]` the same NaN arrives as `null`, which is
  what `store_module.finite` already does for event rows. Same rule as above,
  and one more reason for it. **Corrected during implementation:** a NaN
  seeded by raw SQL never reaches a builder, because the reader already turns
  it into None (`store_reads._stamp` → `store.finite`). The test asserts that
  first, so it keeps saying which guard it is about. It then injects a NaN into
  a builder's output, the second guard, which is the one the MCP owns, and
  checks that the call succeeds with `null` in `structured_content`.
